SLIDE 05 / 17
Concepto · Quién es quién

El servidor sabe de quién son los pedidos por el token

Una página de pedidos tiene un riesgo: que alguien vea los pedidos de otra persona. La defensa no está en React. Está en cómo el servidor decide a quién pertenece la petición.

El navegador dice quién es
GET /api/ordenes?usuario=123. Cualquiera cambia el número y lee los pedidos de otro. Es el mismo error de S32: confiar en lo que llega del navegador.
→
El token lo dice, y el servidor lo verifica
El token se firmó en el login y no se puede falsificar. El servidor lo abre y saca el id de la persona: req.usuario.id. No hay nada que cambiar.
backend/routes/ordenes.js — la consulta (esto ya existe)
1router.get("/", verificarToken, async (req, res) => {
2 const ordenes = await Orden
3 .find({ usuario: req.usuario.id })
4 ...
5})
ParteQué hace
verificarTokenUn guardia delante de la ruta. Sin token responde 401; con un token falso o vencido, 403. Si todo está bien, deja pasar
req.usuario.idEl id que el servidor sacó del token. La petición no trae ningún "usuario" que se pueda cambiar
find({ usuario: ... })El filtro: solo las órdenes cuyo dueño es esa persona. Ana y Beto llaman a la misma ruta y reciben listas distintas

Práctica · ordenes.js

Más nuevos primero, y con imagen

La ruta funciona, pero tiene tres detalles por pulir: las órdenes llegan en cualquier orden, los productos no traen imagen y se devuelven datos que no hacen falta.

backend/routes/ordenes.js — GET / (mis órdenes)
1router.get("/", verificarToken, async (req, res) => {
2 try {
3 const ordenes = await Orden
4 .find({ usuario: req.usuario.id })
5 .populate("productos.producto", "nombre precio imagen")
6 .sort({ createdAt: -1 });
7 res.json(ordenes);
ParteQué hace
.populate("productos.producto", "nombre precio imagen")Cada línea de la orden guarda solo el _id del producto. populate lo cambia por el producto de verdad, pero solo con esos tres campos. Se agrega imagen
.sort({ createdAt: -1 })Ordena por fecha de creación. El -1 significa de la más nueva a la más vieja: arriba va tu compra de hoy
Se quita .populate("usuario", ...)Eran tu nombre y tu correo, que el navegador ya conoce. Se envía solo lo que la página necesita
Un detalle que puede sorprender
El precio que verás viene del producto de hoy, no del día de la compra. Si el producto sube de precio, el pedido viejo mostraría otro valor. Por eso la orden guarda su propio total: es el que se muestra.
SLIDE 07 / 17
Concepto · Estados de una carga

Pedir datos no es instantáneo: la página debe decir qué pasa

Entre pedir los datos y tenerlos, la página pasa por varias situaciones. Cada una necesita su propia pantalla, o la persona ve un espacio en blanco sin saber qué ocurre.

Cargando
La petición salió y no ha vuelto. Se muestra "Cargando tus pedidos…". cargando empieza en true.
Error
El servidor no respondió o respondió mal. Se explica qué revisar. Se guarda en error.
Vacío
Todo salió bien, pero la lista tiene cero pedidos. Se invita a comprar. No es un error: es una cuenta nueva.
Con pedidos
Llegó la lista. Se dibuja una tarjeta por pedido, con el más nuevo arriba.
MisPedidos.jsx — los tres estados
1const [pedidos, setPedidos] = useState([])
2const [cargando, setCargando] = useState(true)
3const [error, setError] = useState("")
Cuatro pantallas con tres estados
"Vacío" no necesita un estado propio: sale de preguntar pedidos.length === 0. No guardes lo que puedes calcular, como el total del carrito en S31.

Práctica · El efecto de MisPedidos

Un efecto pide los pedidos, con el token en la cabecera

Es el patrón de S24, con un ingrediente nuevo: el token. La página lo manda en la cabecera Authorization, igual que Postman.

pages/MisPedidos.jsx — el efecto
1useEffect(() => {
2 if (!usuario) return
3
4 async function cargar() {
5 try {
6 const respuesta = await fetch("http://localhost:3000/api/ordenes", {

8 })
9 if (respuesta.status === 401 || respuesta.status === 403) { ... }
10 if (!respuesta.ok) throw new Error("respuesta no válida")
11
12 setPedidos(await respuesta.json())
13 } catch {
14 setError("No se pudieron cargar tus pedidos...")
15 } finally {
16 setCargando(false)
17 }
18 }
19 cargar()
20}, [])
ParteQué hace
if (!usuario) returnSin sesión no se le pide nada al servidor. La página mostrará un mensaje para ingresar
Authorization: "Bearer " + tokenEl token que guardó el Login. Es lo que el servidor abre para saber quién eres
respuesta.okEs true si el servidor respondió bien. Si no, se lanza un error para ir al catch

finallySe ejecuta siempre, haya salido bien o mal. Aquí apaga "cargando": en los dos casos la espera terminó

Práctica · Casos de sesión

Dos casos: nunca entró, o entró hace mucho

Una página de pedidos solo tiene sentido con sesión. Pero hay dos formas de no tenerla, y cada una pide una respuesta.

CasoCómo lo detecta la páginaQué hace
Nunca inició sesiónusuario es null en el contextoMuestra "Inicia sesión para ver tus pedidos" y un botón a /login, con el aviso y la vuelta a Mis Pedidos
Tenía sesión, pero el token vencióEl servidor responde 403 ("token inválido o expirado"). Sin token, 401Cierra la sesión, y lleva a /login con "Tu sesión terminó..."

Es el mismo viaje de S31
aviso y desde viajan en el state del router. El Login ya los lee: muestra el aviso y, al entrar, regresa a /mis-pedidos. Por qué cerrar la sesión: con un token vencido, usuario seguiría lleno y el Navbar diría "Hola" aunque ya no sirva.
Esto se generaliza en S35
Hoy lo resolvemos en esta página. En S35 se convierte en un componente que protege todas las rutas privadas con un loading global y el manejo del token vencido en un solo lugar.

Los conceptos nuevos de hoy

Todo lo de S19 a S32 sigue funcionando igual. Esto es lo que se suma.

ConceptoQué significa
El token define quién eresEl servidor saca la identidad del token, nunca de un dato que mande el navegador. Por eso cada quien ve solo sus pedidos
populate y sortpopulate cambia un id guardado por el documento completo; sort({ createdAt: -1 }) pone lo más nuevo primero
Estados de una cargaCargando, error, vacío y con datos: cada situación tiene su pantalla. Vacío se calcula, no se guarda
try / catch / finallyfinally se ejecuta siempre: ideal para apagar "cargando" tanto si salió bien como mal
findIndexDevuelve la posición del primer elemento que cumple una condición, o -1 si ninguno
Un componente según su posiciónComparar i con actual decide el aspecto de cada paso: hecho, actual o pendiente
Retornar nullUn componente que devuelve null no dibuja nada. Sirve para casos que no aplican
401 frente a 403401: no hay token. 403: el token no sirve (falso o vencido). En ambos, la página cierra la sesión y manda a ingresar

Criterios de evaluación
  • GET /api/ordenes devuelve solo las órdenes de quien trae el token, las más nuevas primero y con nombre, precio e imagen de cada producto
  • Con dos cuentas distintas en Postman, cada una recibe solo sus pedidos; sin token responde 401 y con un token falso, 403

  • La página tiene respuesta para cuatro casos: cargando, error de conexión, cuenta sin pedidos y lista con pedidos
  • Sin sesión pide ingresar; con un token vencido cierra la sesión y lleva al login con aviso, y al entrar vuelve a Mis Pedidos
  • Al cambiar el estado de una orden en Compass, la línea de tiempo avanza al recargar
  • El enlace "Mis pedidos" aparece solo con sesión, y "Pago aprobado" ofrece "Ver mis pedidos"
  • Sin errores en consola ni en las terminales, y sin scroll horizontal a 390px de ancho
