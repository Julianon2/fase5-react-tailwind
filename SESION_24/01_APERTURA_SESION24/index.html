Concepto

fetch — pedirle datos a un servidor

fetch no es de React — es una función del navegador (JavaScript puro) para hacer peticiones HTTP a una URL, igual a como lo hacía Postman.

fetch básico — pedir y convertir a JSON
1fetch('http://localhost:3000/api/productos')
2 .then((respuesta) => respuesta.json())
3 .then((datos) => console.log(datos))
// las 3 líneas, en palabras normales
fetch(url) = hacer la petición  ·  .json() = convertir la respuesta  ·  datos = el array ya usable
↓ ↓ ↓
"Pide los datos a esa URL, convierte la respuesta a algo que JavaScript entienda, y haz algo con esos datos."
¿Por qué .then() dos veces?
La respuesta de fetch no llega de inmediato — es asíncrona, toma un momento (como esperar la respuesta de Postman). .then() dice "cuando esto termine, haz lo siguiente". El primer .then() espera la respuesta cruda; el segundo espera a que esa respuesta se termine de convertir a JSON.

Concepto

useEffect — código que se ejecuta solo, al cargar

El fetch necesita ejecutarse una vez, apenas el componente aparece en pantalla — no cada vez que algo cambia, ni dentro de un clic. Para eso existe el Hook useEffect.

useEffect con fetch
1import { useState, useEffect } from 'react'
2
3const [productos, setProductos] = useState([])
4
5useEffect(() => {
6 fetch('http://localhost:3000/api/productos')
7 .then((res) => res.json())
8 .then((datos) => setProductos(datos))
9}, [])
// las partes clave, en palabras normales
useEffect(() => {...}) = qué hacer  ·  [ ] = cuándo hacerlo
↓ ↓
"Ejecuta este código, pero solo una vez, apenas el componente aparece en pantalla — nunca más después."
ParteQué es
useEffect(fn, deps)Recibe 2 argumentos: la función a ejecutar, y un array que controla cuándo se repite
[] (array vacío)"No dependas de nada" — el efecto corre una sola vez, al montar el componente
useState([])El catálogo empieza vacío — se llena cuando fetch termine de traer los datos
Sin el array [], se repite sin parar
Si se omite el segundo argumento de useEffect, el efecto se ejecuta después de cada render — y como setProductos provoca un nuevo render, se entra en un ciclo infinito de peticiones al servidor. El [] es lo que evita eso.

Concepto

loading y error — dos useState más

Además de productos, se necesitan 2 estados más para controlar qué se muestra en cada momento.

Los 3 estados completos
1const [productos, setProductos] = useState([])
2const [cargando, setCargando] = useState(true)
3const [error, setError] = useState(null)
4
5useEffect(() => {
6 fetch('http://localhost:3000/api/productos')
7 .then((res) => res.json())
8 .then((datos) => setProductos(datos))
9 .catch(() => setError('No se pudo conectar al servidor'))
10 .finally(() => setCargando(false))
11}, [])
ParteQué hace
useState(true) para cargandoEmpieza en true — apenas arranca el componente, ya está cargando
useState(null) para errorEmpieza en null (sin error) — solo cambia si algo falla
.catch(() => ...)Se ejecuta solo si el fetch falla (servidor caído, sin red)
.finally(() => ...)Se ejecuta siempre al final, haya éxito o error — apaga el estado de carga
Por qué .finally() y no repetir setCargando(false) dos veces
Sin .finally(), habría que escribir setCargando(false) tanto en el caso de éxito como en el de error — .finally() garantiza que se ejecute en ambos casos, sin duplicar código.

Concepto

Mostrar algo distinto según el estado

Con los 3 estados listos, el JSX decide qué mostrar — usando el mismo patrón condición && (...) visto en S23.

Dentro del return de App.jsx
1{cargando && <p>Cargando productos...</p>}
2{error && <p>{error}</p>}
3{!cargando && !error && (
4 <section>{productos.map(...)}</section>
5)}
LíneaSe muestra cuando...
cargando && ...cargando es true — mientras se espera la respuesta
error && ...error tiene un mensaje — algo falló
!cargando && !error && ...ya terminó de cargar Y no hubo error — el caso normal
Sin esto, un momento incómodo
Si no se controla cargando, el catálogo intenta dibujarse con productos vacío apenas carga la página — se ve un parpadeo de "0 resultados" antes de que lleguen los datos reales.

Antes de empezar

Prerequisitos

Hoy es la primera vez que se necesitan DOS servidores corriendo al mismo tiempo.

Backend corriendo
El servidor de la Fase 3 debe estar activo en localhost:3000 — es el que ya usaste con Postman en S11-S16.
Frontend corriendo
npm run dev en frontend-react/ — en localhost:5173, como siempre.
Base de datos con productos
MongoDB Atlas debe tener al menos un producto guardado — si está vacía, el catálogo cargará bien pero se verá sin tarjetas.
CORS ya configurado
El backend ya tiene app.use(cors()) desde la Fase 3 — React puede consumirlo sin fricción, sin instalar nada nuevo.
Un olvido muy común hoy
Si el backend no está corriendo, fetch va a fallar — y gracias al .catch() de hoy, en vez de romper la página, se va a ver el mensaje de error controlado. Ese es, de hecho, el primer caso real para probarlo.
