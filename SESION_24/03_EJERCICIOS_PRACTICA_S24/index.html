Ejercicios de Práctica — useEffect y Fetch

SENA ADSO · Ficha 3229944 · Octubre 2026

Estos ejercicios son opcionales, para reforzar lo aprendido en 02_GUIA_USEEFFECT_FETCH.html si sobra tiempo en la sesión. No introducen conceptos nuevos.
¿Qué practicamos aquí?
Más control sobre cuándo se pide la información, y un error real a propósito

Sin componentes nuevos — se trabaja sobre el fetch y los estados que ya existen en App.jsx. Se practica volver a pedir los datos manualmente, contar resultados reales, y reconocer un error de URL.

Ejercicio 1

Botón para recargar los productos

useEffect con [] solo corre una vez. Si alguien agrega un producto nuevo a la base de datos mientras la página ya está abierta, no aparece hasta recargar el navegador. Este ejercicio agrega un botón para pedirlo de nuevo sin recargar.

1

En App.jsx, sacar la lógica del fetch del useEffect a su propia función, justo antes del useEffect:

frontend-react/src/App.jsxantes
useEffect(() => {
  fetch("http://localhost:3000/api/productos")
    .then((res) => res.json())
    .then((datos) => setProductos(datos))
    .catch(() => setError("No se pudo conectar al servidor"))
    .finally(() => setCargando(false));
}, []);
frontend-react/src/App.jsxdespués
function cargarProductos() {
  setCargando(true);
  setError(null);
  fetch("http://localhost:3000/api/productos")
    .then((res) => res.json())
    .then((datos) => setProductos(datos))
    .catch(() => setError("No se pudo conectar al servidor"))
    .finally(() => setCargando(false));
}

useEffect(() => {
  cargarProductos();
}, []);
ParteQué hace
function cargarProductos()La misma lógica de antes, ahora en una función con nombre que se puede llamar cuando se quiera
setCargando(true) / setError(null)Reinicia los estados antes de cada nueva petición — importante para que "Cargando..." se vea otra vez
useEffect(() => { cargarProductos(); }, [])Sigue llamándola una sola vez al cargar la página, igual que antes
2

En el return de App.jsx, localizar el <div className="flex items-center gap-3">> que contiene el <input> del buscador (y el contador de S23, si lo tienes) — ahí mismo, como último elemento dentro de ese <div>, agregar el botón:

frontend-react/src/App.jsxagregar
<button
  onClick={cargarProductos}
  className="px-4 py-2 bg-verde text-white rounded-lg font-bold text-sm whitespace-nowrap"
>
  Recargar
</button>

Ese <div> completo debe quedar así (el contenido exacto del tuyo puede variar un poco si aplicaste otros ejercicios de S23):

frontend-react/src/App.jsxcómo queda
<div className="flex items-center gap-3">
  <input
    type="text"
    placeholder="Buscar producto..."
    value={busqueda}
    onChange={(e) => setBusqueda(e.target.value)}
    className="..."
  />
  <p className="...">{productos.filter(...).length} producto(s) encontrado(s)</p>
  <button
    onClick={cargarProductos}
    className="px-4 py-2 bg-verde text-white rounded-lg font-bold text-sm whitespace-nowrap"
  >
    Recargar
  </button>
</div>
Cómo verificar: al hacer clic en "Recargar", debe verse brevemente "Cargando productos..." y luego el catálogo de nuevo — sin recargar la página del navegador.
Ejercicio 2

Cuántos productos trajo la API en total

En S23 se mostró cuántos productos coinciden con la búsqueda. Aquí se agrega, además, cuántos productos reales hay en total en la base de datos.

1

En App.jsx, junto al <p> que ya muestra "producto(s) encontrado(s)" (de S23), agregar un segundo texto con el total real:

frontend-react/src/App.jsxagregar
<p className="text-xs text-texto-dim">
  ({productos.length} en total en la base de datos)
</p>
ParteQué hace
productos.lengthEl total de productos que trajo la API — sin filtrar por búsqueda
La diferencia con el contador de S23: productos.filter(...).length cuenta solo lo que coincide con la búsqueda, mientras que productos.length cuenta el total real, sin importar lo que esté escrito en el input.
Cómo verificar: con el buscador vacío, ambos números deben coincidir. Al escribir algo, el primer número baja (coincidencias) mientras el segundo se mantiene fijo (total real).
Ejercicio 3

Provocar un error de URL a propósito

Este ejercicio es intencional: vas a escribir mal la URL del backend a propósito, para reconocer cómo se ve ese error específico — distinto al de "servidor apagado" que ya probaste en la guía.

1

Con el backend corriendo normalmente, en cargarProductos (o en el useEffect, si no hiciste el Ejercicio 1), cambiar temporalmente la URL para que tenga un error de escritura:

frontend-react/src/App.jsxcambiar temporalmente
fetch("http://localhost:3000/api/productoss")  // ← una "s" de más, a propósito
2

Guardar y recargar localhost:5173. Revisar qué pasa en pantalla y en la consola del navegador (F12 → Console).

Con la URL mal escrita, el servidor responde con un error 404 ("no encontrado") — pero fetch no lo trata como fallo de red, así que .catch() puede no dispararse igual que con el servidor apagado. Es un tipo de error distinto, y vale la pena verlo con tus propios ojos una vez.
3

Restaurar la URL correcta (/api/productos, sin la "s" extra) y guardar. Confirmar que el catálogo real vuelve a aparecer.

Cómo verificar: con la URL corregida, el catálogo real vuelve a cargar normalmente, sin errores en consola.
Recordatorio: estos ejercicios (botón recargar, contador total, error de URL) son de práctica — el botón y el contador se pueden dejar en el proyecto, no afectan el entregable de la guía 02.
