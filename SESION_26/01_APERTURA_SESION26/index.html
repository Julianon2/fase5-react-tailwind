SLIDE 04 / 14
El problema

Props no alcanza cuando hay muchas páginas

Hasta hoy, pasar un dato de un componente a otro ha sido fácil: props, de padre a hijo directo (S22). Pero "¿quién inició sesión?" lo necesitan casi todas las páginas — Navbar, Carrito, Perfil, Admin — no solo un hijo directo.

App
↓
Layout
↓
Página
↓
Navbar (lo necesita)
El dato "usuario" pasa por Layout y Página, que NO lo usan — solo lo reenvían, prop por prop.
Esto tiene nombre: "prop drilling"
Pasar una prop a través de componentes intermedios que no la necesitan, solo para que llegue al que sí la necesita más abajo. Funciona, pero se vuelve difícil de mantener — cada componente de en medio queda "ensuciado" con props que no usa para sí mismo.
SLIDE 05 / 14
Concepto

Context API — un dato disponible para cualquiera

Context es parte de React (no hace falta instalar nada) — crea un "canal" de datos que cualquier componente dentro de él puede leer directamente, sin que nadie se lo pase por props.

Con props
App → Layout → Página → Navbar. El dato atraviesa 3 componentes que no lo necesitan para sí mismos.
VS
Con Context
App provee el dato una vez. Navbar lo lee directo, sin que Layout ni Página sepan que existe.
createContext()
Crea el "canal" — un contenedor vacío que luego se llena con datos reales.
<Contexto.Provider>
Envuelve componentes y les "transmite" el valor — todo lo que esté adentro puede escuchar.
useContext()
El Hook que un componente usa para "sintonizar" ese canal y leer el valor — sin props.
SLIDE 06 / 14
Concepto

Las 3 piezas de todo Context

Un archivo de Context siempre tiene la misma estructura — se repite igual para AuthContext y para CartContext.

Estructura general de un Context
1import { createContext, useState } from 'react'
2
3const MiContexto = createContext()
4
5function MiProvider({ children }) {
6 const [dato, setDato] = useState(null)
7 return (
8 <MiContexto.Provider value={{ dato, setDato }}>
9 {children}
10 </MiContexto.Provider>
11 )
12}
13
14export { MiContexto, MiProvider }
// las 3 piezas, en palabras normales
createContext() = el canal  ·  Provider = quien transmite  ·  children = quien recibe
↓ ↓ ↓
"Crea el canal vacío, un componente lo llena con datos reales y envuelve a todos los que necesitan escucharlo."
ParteQué es
createContext()Crea el objeto Context — todavía sin ningún dato real adentro
{ children }Prop especial — representa todo lo que esté envuelto dentro del Provider
value={{ dato, setDato }}Lo que viaja por el canal — cualquier componente hijo puede leerlo con useContext
SLIDE 07 / 14
Concepto

AuthContext — quién inició sesión, en todas partes

El mismo patrón del slide anterior, aplicado a la sesión del usuario — leyendo lo que el login viejo (main.js) ya guardaba en localStorage.

AuthContext.jsx — lo esencial
1const [usuario, setUsuario] = useState(
2 localStorage.getItem('usuario-nombre')
3)
4
5function login(nombre, token, rol) {
6 localStorage.setItem('token', token)
7 localStorage.setItem('usuario-nombre', nombre)
8 setUsuario(nombre)
9}
10
11function logout() {
12 localStorage.clear()
13 setUsuario(null)
14}
// las 3 piezas, en palabras normales
localStorage.getItem(...) = valor inicial  ·  login() = iniciar sesión  ·  logout() = cerrar sesión
↓ ↓ ↓
"Si ya había sesión guardada, arranca con ese nombre; login guarda y actualiza React; logout borra todo y limpia el estado."
ParteQué hace
useState(localStorage.getItem(...))El estado inicial se lee de localStorage — si ya había sesión, no se pierde al recargar
login(nombre, token, rol)Guarda en localStorage (igual que main.js) Y actualiza el estado de React — ambos a la vez
logout()Limpia localStorage y pone el estado en null — cualquier componente que lea "usuario" se entera al instante
Esto no reemplaza localStorage, lo acompaña
localStorage sigue siendo necesario para que la sesión sobreviva a una recarga de página. Lo que AuthContext agrega es que React se entera de los cambios al instante, sin tener que leer localStorage manualmente en cada componente.
SLIDE 08 / 14
Concepto

CartContext — el carrito, compartido entre páginas

Mismo patrón otra vez — hoy migra la lógica de leerCarrito() / guardarCarrito() de main.js a un Context.

CartContext.jsx — lo esencial
1const [items, setItems] = useState(() => {
2 const guardado = localStorage.getItem('carrito')
3 return guardado ? JSON.parse(guardado) : []
4})
5
6function agregarAlCarrito(producto) {
7 const nuevo = [...items, producto]
8 setItems(nuevo)
9 localStorage.setItem('carrito', JSON.stringify(nuevo))
10}
// las piezas clave, en palabras normales
guardado ? ... : [] = valor inicial  ·  [...items, producto] = array nuevo  ·  agregarAlCarrito = la acción
↓ ↓ ↓
"Si ya había carrito guardado, arranca con esos productos; al agregar uno, se crea una copia del array con el nuevo producto al final."
ParteQué hace
useState(() => {...})Forma "perezosa" de useState — la función solo se ejecuta una vez, al crear el componente, no en cada render
[...items, producto]Crea un array nuevo con todo lo anterior más el producto nuevo — nunca se modifica items directamente
setItems(nuevo) + localStorage.setItem(...)Mismo patrón que AuthContext: actualiza React Y localStorage juntos
items.length reemplaza al badge manual
En main.js, el badge del carrito se actualizaba a mano con badge.textContent = carrito.length. Con CartContext, cualquier componente que lea items.length se actualiza solo — React vuelve a dibujar automáticamente cuando el estado cambia.
SLIDE 09 / 14
Concepto

Conectar los 2 extremos del canal

Los slides 8 y 9 crearon AuthContext y CartContext — pero todavía nadie los está "transmitiendo" ni "escuchando". Faltan 2 pasos: envolver la app con los Providers, y leer el valor con useContext donde haga falta.

Paso 1 — Envolver la app (transmitir)
En main.jsx, <App /> queda rodeada por AuthProvider y CartProvider — los componentes que creó cada archivo de Context (el MiProvider del slide 7, con nombre real).
Paso 2 — Leer el dato (escuchar)
Cualquier componente que esté adentro de esos Providers — como Navbar.jsx — puede usar useContext para leer el valor, sin que nadie se lo pase por props.
Paso 1 — main.jsx (dónde se transmite)
1import { AuthProvider } from './AuthContext.jsx'
2import { CartProvider } from './CartContext.jsx'
3
4<AuthProvider>
5 <CartProvider>
6 <App />
7 </CartProvider>
8</AuthProvider>
Paso 2 — Navbar.jsx (dónde se escucha)
1import { useContext } from 'react'
2import { CartContext } from './CartContext.jsx'
3
4function Navbar() {
5 const { items } = useContext(CartContext)
6 return <span>{items.length}</span>
7}
ParteQué significa
AuthProvider / CartProviderLos componentes exportados por cada archivo de Context (slides 8 y 9) — se usan como etiquetas que envuelven
Anidados uno dentro del otroApp necesita acceso a ambos, así que ambos Providers la envuelven, uno dentro del otro
useContext(CartContext)Se usa dentro de cualquier componente envuelto por CartProvider — aquí, dentro de Navbar
{ items }Extrae directamente el dato items del objeto que entrega el Context — mismo patrón que desestructurar props
Sin el Paso 1, el Paso 2 no funciona
useContext(CartContext) solo trae datos reales si el componente está envuelto por <CartProvider> en algún punto más arriba del árbol — por eso el orden importa: primero se envuelve la app (Paso 1), después se puede leer desde cualquier componente (Paso 2).
