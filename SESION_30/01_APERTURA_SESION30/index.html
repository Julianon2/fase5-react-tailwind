Migrar Login y Registro: la tienda reconoce a sus usuarios

Hasta hoy cualquiera entra a TechStore y el botón "Ingresar" no lleva a ninguna parte. En esta sesión nacen dos páginas con formularios de verdad: una para crear una cuenta y otra para iniciar sesión. El backend responde con un token, React lo guarda, y el Navbar pasa a saludar por tu nombre. En el camino, una lección de seguridad: el navegador nunca es de fiar.

SLIDE 05 / 16
Concepto · Autenticación

Entrar es cambiar tu clave por un token

Una página web no recuerda quién eres entre una petición y otra. El servidor te da, al entrar, un token: un texto firmado que funciona como un pase. React lo guarda y de ahí en adelante se sabe que eres tú.

Formulario — correo y contraseña
↓ POST /api/auth/login ↓
Servidor — compara con el hash de bcrypt
↓ responde { token, nombre, rol } ↓
AuthContext — guarda la sesión
Navbar — saluda por el nombre
La contraseña viaja una sola vez, al entrar. Después solo viaja el token.
Autenticación
Responde "¿quién eres?". Es lo que resuelve el login, y es lo de hoy.
Autorización
Responde "¿qué puedes hacer?". Depende del rol, y llega en S35 con las rutas protegidas.
El token caduca
El de tu backend dura 24 horas. Qué hacer cuando vence también se ve en S35.
Un mensaje igual para dos fallos
Si el correo no existe o la contraseña está mal, el servidor responde lo mismo: "Email o contraseña incorrectos". Es a propósito: así nadie puede descubrir qué correos tienen cuenta.
SLIDE 06 / 16
Concepto · Seguridad

Lo que manda el navegador lo puede escribir cualquiera

El formulario de React ni siquiera tiene un campo "rol". Pero quien abre las herramientas del navegador, o usa Postman, puede mandar cualquier campo que se le ocurra. Las reglas importantes viven en el servidor.

Hoy: el servidor obedece
Lee rol del cuerpo de la petición y lo guarda. Mandar "rol": "admin" crea un administrador sin permiso de nadie.
→
Mañana: el servidor decide
No lee el rol del cuerpo: toda cuenta nueva es "cliente". El administrador se hace aparte, editando el rol en Compass.
backend/routes/auth.js — el registro tras la corrección
1router.post('/registro', async (req, res) => {
2 const { nombre, email, password, departamento, municipio } = req.body
3 // el rol ya no se lee del cuerpo
4 if (!password || password.length < 6) {
5 return res.status(400).json({ error: 'La contraseña debe tener al menos 6 caracteres' })
6 }
7 ...
8})
Dos capas, como en S27
La página avisa rápido y con cariño. El servidor revisa otra vez, porque es el único que nadie puede saltarse.
El administrador se crea en Compass
Registras una cuenta normal y, con la guía de CRUD, cambias su rol a "admin" con updateOne. Solo quien controla la base puede hacerlo.

Tres formularios, un solo Campo

En Contacto.jsx hay un componente pequeño, Campo, que dibuja la etiqueta, el control y el mensaje de error. Login y Registro necesitan lo mismo. En vez de copiarlo tres veces, se saca a su propio archivo.

Campo.jsx — el archivo nuevo

2 return (
3 <div className="flex flex-col gap-1.5">
4 <label htmlFor={nombre}>{etiqueta}</label>
5 {children}
6 {error && <span>{error}</span>}
7 </div>
8 )
9}
10
11export default Campo
Login.jsx — cómo se usa
1<Campo etiqueta="Correo" nombre="email" error={errores.email}>
2 <input id="email" name="email" onChange={manejarCambio} />
3</Campo>
// las 3 piezas, en palabras normales
children = lo que va entre las etiquetas: el input  ·  error = el texto rojo, solo si hay error  ·  onChange = cada letra actualiza el estado
↓ ↓ ↓
"El Campo dibuja la etiqueta y el error; el input que va dentro lo escribe cada página, y cada tecla actualiza el formulario."
ParteQué hace
{children}Es lo que escribes entre las etiquetas de apertura y cierre de <Campo>. Permite que el mismo componente envuelva un input, un select o un textarea

Práctica · Formulario de Login

Enviar, esperar, entrar

El Login es el patrón de Contacto con dos campos y un destino: si la respuesta es buena, se guarda la sesión y se viaja a la página principal.

Login.jsx — el envío
1async function manejarEnvio(e) {
2 e.preventDefault()
3 setEstado("enviando")
4 try {
5 const res = await fetch(URL_API + "/login", { method: "POST", ... })
6 const datos = await res.json()
7 if (!res.ok) throw new Error(datos.error)
8
9 login(datos.nombre, datos.token, datos.rol)
10 navegar("/")
11 } catch (err) {
12 setMensajeError(err.message)
13 setEstado("error")
14 }
15}
Las dos últimas acciones
1login(datos.nombre, datos.token, datos.rol)
2navegar("/")
// las 2 piezas, en palabras normales
login(...) = guardar la sesión en el contexto  ·  navegar("/") = ir a la página principal
↓ ↓
"Guarda quién eres y te lleva al inicio."
ParteQué hace
if (!res.ok) throw new Error(datos.error)Un 401 llega como respuesta normal. Se lanza el error a mano para que lo atrape el catch, que muestra el texto que mandó el servidor
login(nombre, token, rol)La función de AuthContext (S26): guarda los tres datos y avisa a toda la tienda
useNavigate()El hook del router (S25) que devuelve una función para cambiar de página desde el código, no con un enlace
type="password"El input oculta lo que se escribe. Solo es presentación: la seguridad real la hace el servidor

Concepto · Sesión persistente

La sesión sobrevive a recargar... y a salir

Al recargar la página React empieza de cero. Por eso el estado inicial se lee de localStorage. Y por eso hay un detalle en logout que, si no se corrige, borra algo que no debería.

logout con localStorage.clear()
Borra todo lo guardado, también el carrito ("carrito"). Al recargar la página después de salir, las compras habrían desaparecido.
→
Solo las 3 claves de sesión
removeItem para el token, el nombre y el rol. El carrito queda donde estaba.
AuthContext.jsx — la parte nueva
1const [usuario, setUsuario] = useState(localStorage.getItem("usuario-nombre"))
2const [rol, setRol] = useState(localStorage.getItem("usuario-rol"))
3
4function logout() {
5 localStorage.removeItem("token")
6 localStorage.removeItem("usuario-nombre")
7 localStorage.removeItem("usuario-rol")
8 setUsuario(null)
9 setRol(null)
10}
localStorage: sencillo para aprender
Guardar el token en localStorage es lo más simple y sirve para esta fase. En un producto real se discuten otras opciones, como las cookies protegidas. Hoy basta con saber que existe esa decisión.
SLIDE 10 / 16
Concepto · Dos selects encadenados

El municipio depende del departamento

Un colombiano no puede elegir "Garzón" sin haber elegido "Huila". El segundo select no tiene opciones propias: las pide cada vez que cambia el primero. Es un useEffect con dependencia, como el del detalle de producto de S29.

Departamento — Huila
↓ cambia el id ↓
useEffect([departamentoId]) — pide las ciudades
↓ API Colombia ↓
Municipio — Garzón, Pitalito, Neiva…
Y si cambias de departamento, el municipio elegido antes deja de tener sentido: se limpia.
Registro.jsx — el efecto de los municipios
1useEffect(() => {
2 if (!departamentoId) return
3 fetch("https://api-colombia.com/api/v1/Department/" + departamentoId + "/cities")
4 .then((res) => res.json())
5 .then((datos) => setMunicipios(datos))
6}, [departamentoId])
Una API pública
api-colombia.com entrega los departamentos y las ciudades de cada uno. No necesita clave ni cuenta.
Limpiar al cambiar
Al elegir otro departamento, el municipio guardado se borra y la lista nueva empieza vacía.
Se guarda el nombre
El backend recibe el nombre ("Huila", "Garzón"), no el número de la API. El id solo sirve para pedir las ciudades.

Práctica · Formulario de Registro

Más campos, las mismas ideas

El Registro es el formulario más largo de la tienda, pero no trae nada nuevo: un estado con un objeto, un validar, un fetch y estados de envío. Solo cambia lo que se valida.

Registro.jsx — la validación de la contraseña
1if (form.password.length < 6) nuevos.password = "Mínimo 6 caracteres"
2if (form.confirmar !== form.password) nuevos.confirmar = "Las contraseñas no coinciden"
// las 2 reglas, en palabras normales
length < 6 = una contraseña corta es débil  ·  confirmar !== password = las dos veces deben ser iguales
↓ ↓
"La contraseña tiene al menos 6 caracteres y se escribe dos veces igual para evitar errores de tipeo."
ParteQué hace
confirmarUn campo que solo existe en el formulario: sirve para comparar y no se manda al servidor
Estado del formularioUn solo objeto con nombre, email, password, confirmar, departamento y municipio, y un único manejarCambio que sirve para todos (S27)
Tras el éxitoSe viaja a /login con un aviso de "cuenta creada". Se entra con la cuenta recién hecha, sin iniciar sesión sola
Correo repetidoEl servidor responde "El email ya está registrado" y la página lo muestra: es un error que solo el servidor puede saber
Mira tu usuario en Compass
Cada cuenta que registres aparece en techstore → usuarios de tu base local, con la contraseña encriptada: nunca se ve la contraseña real. Es la colección que la guía de CRUD dejó vacía a propósito.
