Paso 1 · Backend

Un registro que no se deja engañar

Antes de abrir la puerta de la tienda hay que revisar la cerradura. Hoy POST /api/auth/registro lee el campo rol que manda el navegador, y quien use Postman puede crear un administrador. Primero lo compruebas con tus propios ojos, y después lo arreglas. Se cambia un solo archivo: backend/routes/auth.js.

1

Levanta los dos servidores, cada uno en su terminal, con la base local activa (la rutina de la sesión extra):

terminal 1 — dentro de backend/
npm run dev
terminal 2 — dentro de frontend-react/
npm run dev
Cómo verificar: en localhost:3000 el navegador muestra "baseDeDatos":"local" y localhost:5173 muestra la tienda. Si dice "atlas", cambia DB_MODO=local en el .env, guarda y escribe rs en la terminal del backend: hoy se crean usuarios y no deben ir a Atlas.
2

Mira el hueco antes de taparlo. En Postman crea una petición nueva: método POST, dirección http://localhost:3000/api/auth/registro. En Body elige raw y JSON, y escribe:

Postman — Body (raw, JSON)
{
  "nombre": "Intruso Uno",
  "email": "intruso@correo.com",
  "password": "123",
  "departamento": "Huila",
  "municipio": "Garzón",
  "rol": "admin"
}

Pulsa Send. Después abre Compass, conéctate a TechStore Local y en techstore → usuarios mira el documento nuevo (o en la consola: db.usuarios.find({ email: "intruso@correo.com" })).

Cómo verificar: Postman responde 201 con "Usuario creado correctamente". En Compass el usuario tiene rol: "admin", y la contraseña está encriptada, aunque solo tenía 3 caracteres. Alguien sin permiso de nadie se hizo administrador con un campo extra.
Por qué pasa: el formulario de React nunca tendrá un campo "rol", pero eso no protege nada. Quien abre Postman o las herramientas del navegador manda cualquier campo que se le ocurra. Lo que llega del cliente puede ser falso: las reglas importantes se revisan en el servidor.

    const usuario = await Usuario.findOne({ email });
