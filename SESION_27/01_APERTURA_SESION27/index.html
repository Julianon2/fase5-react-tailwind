SLIDE 04 / 16
Diseño

Landing continuo: espacio, no bordes

La regla fija de la identidad premium: la página debe sentirse como un solo scroll, sin cortes duros entre secciones. Lo que separa un bloque de otro es el espacio en blanco, y el cambio de blanco a negro se resuelve con un degradado largo.

Lo que ya no hacemos
border-b debajo del navbar, bloques con fondo distinto por sección y un footer negro que "corta" la página de golpe.
→
Lo que hacemos hoy
Secciones separadas por gap y padding, y un footer cuyo fondo es un degradado que empieza en blanco y termina en negro.
Footer.jsx — el degradado
1<footer className="bg-linear-to-b from-paper to-ink to-60% pt-48">
// las 4 piezas, en palabras normales
bg-linear-to-b = degradado hacia abajo  ·  from-paper = empieza blanco  ·  to-ink to-60% = llega a negro  ·  pt-48 = espacio para que se note
↓ ↓ ↓ ↓
"Pinta el fondo en degradado: arriba es blanco, al 60% de la altura ya es negro, y con mucho espacio arriba para que el cambio sea lento."
ClaseQué hace
bg-linear-to-bFondo en degradado lineal que va de arriba hacia abajo (to-b = "to bottom")
from-paperColor de arranque: --color-paper, el blanco puro del tema
to-ink to-60%Color final (--color-ink, negro casi puro) y el punto donde ya se alcanza: el 60% de la altura del footer
pt-4812rem (192px) de espacio arriba del contenido: es el "tramo" donde ocurre el cambio de color

Concepto

Quitarle la caja a App.jsx

Hoy App.jsx mete Navbar, rutas y Footer dentro de un único <main max-w-6xl>. Con esa caja el footer nunca puede ocupar todo el ancho ni degradarse hasta el borde de la pantalla.

Antes (S25)
Una sola caja de 1152px de ancho máximo contiene todo: Navbar, página y Footer quedan encerrados juntos.
→
Después (hoy)
App es una columna a todo el ancho. Navbar y las páginas llevan su propio contenedor; el Footer ocupa el ancho completo.
min-h-screen flex flex-col
La columna raíz mide al menos toda la pantalla, así el footer siempre queda abajo aunque la página sea corta.
flex-1 en el main
El contenido toma todo el espacio sobrante y empuja el Footer al fondo.
max-w-6xl mx-auto px-6
El contenedor centrado ahora lo declara cada zona que lo necesita, no la app entera.

Concepto

El wordmark y los enlaces activos

La marca de TechStore Pro es solo texto: sin logo ni ícono junto a ella. Y los enlaces del Navbar pasan de un ternario repetido a una lista que se recorre con .map().

Navbar.jsx — el wordmark
1<Link to="/" className="font-wordmark text-xl tracking-wide">
2 TECH<span className="text-accent-dark">STORE</span>
3</Link>
font-wordmark
Tailwind crea esta clase a partir del token --font-wordmark que definió index.css en la sesión de rebranding: la fuente Michroma.
text-accent-dark solo en "STORE"
El coral aparece en un único punto de la marca. Se usa la versión oscura porque Michroma tiene un trazo fino y necesita contraste. Con moderación, el acento se nota más.
NavLink en vez de Link
NavLink avisa si su ruta es la actual (isActive), sin necesidad de comparar useLocation().pathname a mano en cada enlace.
Un array de enlaces + .map()
Los 4 enlaces viven en un array de objetos. Agregar uno nuevo es agregar una línea, como en S22 con los productos.

Página 2

Nosotros: el contenido vive en arrays

En nosotros.html había que copiar y pegar un bloque por cada integrante del equipo. En React el bloque se escribe una vez y los datos se guardan aparte.

HTML viejo
Tres bloques .miembro casi idénticos. Para sumar un cuarto integrante, se copia todo el bloque.
→
React
Un array equipo con un objeto por persona y un solo bloque dentro de .map(). Sumar un integrante es sumar un objeto.
Nosotros.jsx — datos y dibujo
1const equipo = [
2 { nombre: "Integrante 1", cargo: "Frontend" },
3 { nombre: "Integrante 2", cargo: "Backend" },
4]
5
6{equipo.map((persona) => (
7 <div key={persona.nombre}>{persona.cargo}</div>
8))}
Datos separados del diseño
Cambiar un nombre o un cargo es editar un texto del array, sin tocar etiquetas.
key en cada elemento
Igual que con los productos en S22: React necesita un identificador único para no confundir elementos.
Tu equipo real
La guía trae datos de ejemplo. Al terminar, cada aprendiz reemplaza los integrantes por los de su grupo.

Concepto

Un formulario con muchos campos, un solo estado

En S23 el buscador tenía un campo y un useState. Contacto tiene cinco campos: en vez de cinco estados, se guarda un objeto y una sola función lo actualiza.

Contacto.jsx — actualizar cualquier campo
1function manejarCambio(e) {
2 setForm({
3 ...form,
4 [e.target.name]: e.target.value
5 })
6}
7
8<input name="email" value={form.email} onChange={manejarCambio} />
// las 3 piezas, en palabras normales
...form = copia todo lo que había  ·  [e.target.name] = qué campo cambió  ·  e.target.value = lo que se escribió
↓ ↓ ↓
"Conserva los demás campos, y en el campo que disparó el evento pon lo que el usuario acaba de escribir."
ParteQué hace
...form"Spread": copia todos los campos del objeto actual al nuevo. Así no se pierde lo ya escrito en los otros campos
[e.target.name]Corchetes: usar el valor del name del input (por ejemplo "email") como nombre de la propiedad
e.target.valueEl texto que hay ahora mismo en el input que disparó el evento
name="email" en el inputEs la conexión: el name del input debe ser igual a la propiedad del objeto form
Si el name no coincide, el campo no se actualiza
Un name="correo" en el input crearía una propiedad nueva correo en el objeto, y form.email seguiría vacío. Es el error más común de este patrón.
SLIDE 10 / 16
Seguridad

Validar en el navegador Y en el servidor

Una tienda real no puede confiar en lo que llega desde el navegador: cualquiera puede saltarse la página y llamar a la API directamente. Por eso cada dato se valida dos veces, con propósitos distintos.

Usuario escribe en el formulario
↓
React valida (rápido, sin red)
↓ solo si pasa: fetch POST /api/contacto
Express + Mongoose validan (la defensa real)
↓ solo si pasa
MongoDB Atlas guarda el mensaje
Dos controles en cadena: el segundo no depende de que el primero haya corrido.
Validación en React
Para qué: dar respuesta inmediata al usuario ("falta el @ en el correo") sin esperar a la red. Se puede saltar: sí, con las herramientas del navegador o con Postman.
+
Validación en el backend
Para qué: garantizar que ningún dato inválido entre jamás a la base de datos. Se puede saltar: no, es el único punto que el usuario no controla.

Backend

Un modelo y una ruta nuevos

Mismo patrón que Producto y Usuario en la Fase 3: un modelo con las reglas del dato y una ruta que lo recibe. Es la primera vez que el backend se toca en la Fase 5.

Bloque 1 — models/Mensaje.js (las reglas)
1nombre: {
2 type: String,
3 required: [true, 'El nombre es obligatorio'],
4 minlength: [3, 'El nombre es muy corto']
5}
required / minlength
Las reglas se declaran en el esquema. Mongoose las revisa solo antes de guardar.
[valor, "mensaje"]
El segundo elemento es el texto del error en español, el mismo que el formulario le mostrará al usuario.
Bloque 2 — routes/contacto.js (la puerta)
1router.post('/', async (req, res) => {
2 const { nombre, email, asunto, mensaje } = req.body
3 await Mensaje.create({ nombre, email, asunto, mensaje })
4 res.status(201).json({ mensaje: 'Mensaje recibido' })
5})
Se toman solo los campos esperados
Si alguien envía un campo extra (por ejemplo leido: true), se ignora: solo pasan los 4 que se desestructuran.
Ruta pública
A diferencia de crear productos, no lleva verificarToken: cualquier visitante puede escribir. Leer los mensajes, en cambio, será solo para admin (S34).

Concepto

Los 4 estados de un envío

Enviar un formulario toma tiempo y puede fallar. Una sola variable de estado, estado, describe en qué punto va el formulario, y la pantalla cambia según su valor.

1
"inactivo"
Escribiendo
Estado inicial. El botón dice "Enviar mensaje" y está habilitado.
2
"enviando"
Esperando al servidor
El botón queda deshabilitado y dice "Enviando...". Evita que el usuario envíe dos veces.
3
"exito"
Mensaje guardado
Aparece la confirmación y el formulario se vacía.
4
"error"
Algo falló
Se muestra el error que devolvió el servidor, y lo escrito se conserva para reintentar.
try / catch con async / await
Es la misma idea de .then() y .catch() de S08 y S24, escrita en forma de lectura lineal: await pausa la función hasta que llegue la respuesta, y si algo falla el código salta al bloque catch.

ConceptoQué significa
