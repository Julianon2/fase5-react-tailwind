El problema

¿Por qué no alcanza con una variable normal?

Hasta ahora, cada vez que algo cambiaba en pantalla, era porque React volvía a renderizar el componente desde cero con props nuevas (S22). Pero un contador no recibe props nuevas desde afuera — el cambio tiene que nacer adentro del componente mismo.

Lo que NO funciona (aunque parezca lógico)
1function Contador() {
2 let cuenta = 0 // variable normal de JavaScript
3
4 function sumar() {
5 cuenta = cuenta + 1 // esto SÍ cambia la variable...
6 }
7
8 return <button onClick={sumar}>{cuenta}</button>
9}
❌
¿Qué pasa al hacer clic?
La variable cuenta sí cambia en memoria... pero React nunca se entera de que cambió, así que nunca vuelve a dibujar el botón. El número en pantalla se queda congelado en 0 para siempre, aunque la variable por dentro sí valga 1, 2, 3.
⚠️
No es un error de sintaxis
Este código no tiene ningún error — compila y corre sin problema. El fallo es conceptual: una variable normal de JavaScript no tiene forma de avisarle a React "oye, algo cambió, vuelve a dibujar". Para eso existe useState.

Concepto

useState — una variable que React sí vigila

useState es un Hook — una función especial de React que le da a un componente la capacidad de "recordar" un valor entre renders, y de avisarle a React cuando ese valor cambia.

La versión que sí funciona
1import { useState } from 'react'
2
3function Contador() {
4 const [cuenta, setCuenta] = useState(0)
5
6 return <button onClick={() => setCuenta(cuenta + 1)}>{cuenta}</button>
7}
// línea 4, en palabras normales
useState(0) = la cajita  ·  cuenta = valor actual  ·  setCuenta = función para cambiarlo
↓ ↓ ↓
"Crea una cajita que empieza en 0, dame algo para leerla y algo para cambiarla."
// línea 6, en palabras normales
onClick = cuándo pasa  ·  setCuenta(cuenta+1) = qué hacer  ·  {cuenta} = qué mostrar
↓ ↓ ↓
"Cuando hagan clic, suma 1 al valor guardado, y en el botón muestra siempre el valor actual."
// prueba esto mismo — es exactamente lo que vas a construir
0
ParteQué es
useState(0)Crea una "caja" de estado, con valor inicial 0 — React la recuerda entre renders
cuentaEl valor actual guardado — se lee igual que cualquier variable
setCuentaLa única forma correcta de cambiar ese valor — nunca se reasigna cuenta directamente
[cuenta, setCuenta]useState siempre devuelve un array de 2 elementos: el valor y su función para cambiarlo
✅ La diferencia clave
Llamar a setCuenta(...) no solo cambia el valor — también le dice a React "vuelve a dibujar este componente con el valor nuevo". Eso es lo que la variable normal del slide anterior nunca podía hacer.
💡
¿Qué es exactamente un "Hook"?
Un Hook es una función especial de React que siempre empieza con la palabra use — useState es el primero que vemos, pero no el único que existe (más adelante, en S24, aparece useEffect). Lo que los hace especiales es que "enganchan" un componente normal a capacidades internas de React — como recordar un valor entre renders — que una función de JavaScript común no tiene por sí sola.
⚠️
¿Por qué la demo puede bajar a -1, -2...?
function Contador() no decide ningún límite — eso depende únicamente de lo que se escriba dentro de setCuenta(...). Como el ejemplo de arriba solo usa setCuenta(cuenta + 1), sin condición, el botón "−" también resta sin tope. Para evitarlo, haría falta una condición en ese botón:
<button onClick={() => setCuenta(cuenta > 0 ? cuenta - 1 : 0)}>−</button>

Concepto

Eventos — cómo React escucha al usuario

Un evento es algo que el usuario hace: un clic, escribir en un campo, pasar el mouse. JSX los maneja con atributos especiales, parecidos al HTML normal pero con una diferencia clave.

HTML normal vs JSX (React)
1// HTML normal
2<button onclick="sumar()">+</button>
3
4// JSX (React)
5<button onClick={sumar}>+</button>
// las 2 diferencias, en palabras normales
onclick → onClick  ·  "sumar()" → {sumar}
↓ ↓
"El nombre del evento pasa a camelCase, y la función ya no es texto entre comillas — es código real entre llaves, sin ejecutarla ahí mismo."
🖱️
onClick
Se dispara al hacer clic — el que ya se usó en el contador, para el botón "+".
⌨️
onChange
Se dispara cada vez que el valor de un <input> cambia — una letra, un carácter, cada tecla cuenta.
📦
El evento (e)
La función que maneja el evento recibe un parámetro con información — e.target.value es lo que el usuario escribió.
⚠️ {sumar} vs {sumar()}
Con llaves y sin paréntesis (onClick={sumar}) se le pasa la función a React para que la ejecute cuando ocurra el clic. Con paréntesis (onClick={sumar()}) la función se ejecuta de inmediato al renderizar, no al hacer clic — error muy común.

Concepto

El input "controlado" — su valor vive en useState

En HTML normal, un <input> guarda su propio valor internamente. En React, se prefiere que ese valor viva en useState — así el componente siempre sabe exactamente qué hay escrito, en cualquier momento.

Input controlado — la estructura completa
1const [busqueda, setBusqueda] = useState("")
2
3<input
4 value={busqueda}
5 onChange={(e) => setBusqueda(e.target.value)}
6/>
// la estructura completa, en palabras normales
busqueda = lo que hay escrito  ·  e.target.value = lo que se acaba de teclear
↓ ↓
"El input siempre muestra lo que hay guardado, y cada tecla dispara onChange, que guarda lo nuevo que se escribió."
ParteQué hace
useState("")Estado inicial: texto vacío — el buscador empieza sin nada escrito
value={busqueda}Lo que se ve en el input siempre es exactamente el valor guardado en el estado
onChange={(e) => ...}Cada vez que el usuario teclea algo, se ejecuta esta función
e.target.valueEl texto que quedó en el input justo después de esa tecla
setBusqueda(...)Guarda ese texto nuevo en el estado — y React vuelve a dibujar con el valor actualizado
💡 ¿Por qué no dejar que el input se controle solo?
Porque en el siguiente slide ese mismo valor (busqueda) se va a usar para filtrar el catálogo — si el valor solo viviera dentro del <input> y no en el estado del componente, no habría forma de leerlo desde afuera para compararlo con cada producto.

Concepto

.filter() — del array completo al array visible

Ya usamos .map() en S22 para convertir productos en tarjetas. Hoy se agrega .filter() justo antes, para decidir cuáles productos llegan siquiera a convertirse en tarjeta.

App.jsx — combinando filter() y map()
1{productos
2 .filter((p) => p.nombre.toLowerCase().includes(busqueda.toLowerCase()))
3 .map((p) => <ProductCard key={p.nombre} ... />)}
// la línea clave, en palabras normales
filter = la decisión  ·  p.nombre = nombre del producto  ·  busqueda = lo que se escribió
↓ ↓ ↓
"Por cada producto, pregunta: ¿el nombre contiene lo que escribiste? Si sí, se queda; si no, desaparece."
ParteQué hace
.filter((p) => ...)Recorre el array y se queda solo con los elementos donde la condición es verdadera
p.nombre.toLowerCase()Convierte el nombre del producto a minúsculas, para comparar sin importar mayúsculas
.includes(busqueda.toLowerCase())Verdadero si el nombre contiene el texto buscado — también en minúsculas
.filter(...).map(...)Se encadenan: primero se reduce la lista, después se convierte lo que queda en componentes
💡 ¿Por qué toLowerCase() en los dos lados?
Sin esto, buscar "Mouse" (con mayúscula) no encontraría "mouse inalámbrico" porque JavaScript compara texto de forma exacta, letra por letra, incluyendo mayúsculas y minúsculas. Convertir ambos lados a minúsculas antes de comparar evita ese problema.
